# 減色・パレット・画像キャッシュ設計

このページでは、PVNMの減色処理、シーンパレット構築、画像キャッシュ、VN Palette Toolの画像変換を技術者向けに説明します。

関連実装は主に次のファイルです。

| ファイル | 役割 |
| --- | --- |
| `engine/palette.py` | `MasterColor.pyxpal`の生成/読込、シーンパレット構築 |
| `engine/image_cache.py` | 固定パレット量子化、`.npy`キャッシュ、manifest読込、透明colkey |
| `engine/player.py` | シーンごとのパレット適用、画像先読み |
| `engine/ending_player.py` | エンディングスライド用パレット |
| `engine/gallery_palette.py` | CGギャラリーサムネイル用セピアパレット |
| `vn_palette_tool.py` | 画像素材をPVNM向けに変換する外部ツール |

VN Palette Toolの各UI項目と `0-10` 系パラメータの詳しい式は、専用ページの [VN Palette Tool詳細設計](technical-vn-palette-tool.md) に分けています。

## まず減色アルゴリズムの分類

減色は、フルカラー画像を少ない色数で近似する処理です。代表的な方式には次のようなものがあります。

| 方式 | 概要 | 長所 | 短所 |
| --- | --- | --- | --- |
| 均等量子化 | RGB空間を等間隔の箱に分ける | 実装が単純で速い | 画像に存在しない色にも枠を割き、見た目が荒れやすい |
| 人気色抽出 | 出現回数が多い色を上位から採用 | ドット絵やベタ塗りに強い | グラデーションの中間色に枠を奪われ、差し色が落ちやすい |
| Median Cut | 色集合を分布に沿って再帰分割し、各領域の代表色を選ぶ | 色域を広くカバーしやすく、写真/イラストに強い | 最終的な最近傍割当は別途必要 |
| Octree | RGB空間を木構造に入れ、葉を統合する | インクリメンタルに処理できる | 実装差が大きく、品質調整が必要 |
| k-means | 色をクラスタリングし、重心を代表色にする | 品質を追い込みやすい | 反復計算が重く、初期値で結果が揺れる |
| 固定パレット最近傍 | 既に決めたパレットの最も近い色へ割り当てる | ランタイムの色番号と一致する | パレット自体が悪いと救えない |
| ディザリング | 誤差を周辺に分散、またはパターン化する | 少ない色でも階調を感じさせられる | ノイズ感、ちらつき、UIとの相性問題が出る |

PVNMでは、目的に応じて2段階を分けています。

1. **パレットを作る段階**
   シーンに出る画像群から、代表色256色以内の候補を作ります。ここではPillowのAdaptive Palette、実質的にはMedian Cut系の処理を使います。

2. **固定パレットへ写像する段階**
   決まった256色パレットへ各ピクセルを割り当てます。ここではPillowのC実装 `quantize(palette=...)` を使います。

この2段階分離が重要です。単に画像ごとに `convert("P", palette=ADAPTIVE)` するだけだと、Pyxelで必要なパレットindex、UI予約色、話者色、透明colkey、エクスポートmanifestとの整合が取れません。

## マスターパレットの構造

PVNMの基準パレットは `assets/images/MasterColor.pyxpal` です。存在しない場合や `MasterColor.png` が更新された場合は `engine/palette.py` が生成します。

indexの意味は次のように分かれます。

| index範囲 | 用途 |
| --- | --- |
| `0..15` | エディタUI用の安全領域。背景、パネル、ボタン、文字など |
| `16..255` | `MasterColor.png` から抽出した色 |

`0..15` は、シーンパレットを作るときも原則として固定されます。PVNMは画像ごと、シーンごとにパレットを動かしますが、UIの基本色まで毎回変わると操作画面やメッセージウィンドウの見た目が破綻するためです。

`settings.json` の `dialog_role_indices` と `speaker_colors` で使われているindexも予約色に入ります。たとえば話者Aの本文色をindex 50にしているなら、シーン画像がどれだけ別の色を必要としても、index 50のRGBはマスター値のまま残します。

## シーンパレット構築

シーンパレットは `engine.palette.build_scene_palette(image_paths, reserved, base_dir)` で作られます。

入力は、現在画面に出る可能性がある画像群です。

| 画像種別 | 収集されるもの |
| --- | --- |
| 背景 | 現在シーンの背景、または前シーンから継承された背景 |
| 背景アニメ | `bg_anim.flipbook_files` |
| 立ち絵 | `char_l`、`char_c`、`char_r` の現在表示画像 |
| 立ち絵アニメ | 各キャラの `anim.flipbook_files` |
| エンディング | スライド画像ごと |
| タイトル | タイトル背景とタイトルボタン色の予約 |
| ギャラリー | 詳細表示画像、サムネイル用セピアパレット |

実装上の手順は次の通りです。

```text
image_paths を絶対パスへ解決
  ↓
存在するファイルだけを mtime 付きで記録
  ↓
reserved 色集合とファイルmtimeからキャッシュkeyを作る
  ↓
各画像をRGB化する
  ↓
透明部分を reserved index 0 のRGBで合成する
  ↓
最大辺256pxへ縮小する
  ↓
複数画像を縦に連結する
  ↓
Pillow Adaptive Palette で代表色を多めに抽出する
  ↓
reserved と同じRGBを除外する
  ↓
reserved以外のfree slotへ順に詰める
  ↓
余ったslotは黒で埋める
```

透明部分を `reserved[0]` のRGBで合成するのは、透明領域が独自の代表色としてパレット枠を消費しないようにするためです。透明領域の色が大量に存在すると、Adaptive Paletteはそれを重要な色として扱います。PVNMではその色を予約色と重複させることで、後段の重複除外に流し、free slotを実画像の色へ回します。

## なぜMedian Cut系を使うのか

PVNMの素材は、ドット絵だけでなく、アンチエイリアスの強い立ち絵、グラデーション背景、写真系背景を含みます。この場合、単純な人気色抽出は弱いことがあります。

たとえば肌のグラデーションに微妙に違う色が大量にあると、人気色上位は肌の中間色で埋まります。結果として、目の色、リボン、アクセントライトのような面積は小さいが意味のある色が落ちます。

Median Cut系のAdaptive Paletteは、RGB空間を分布に沿って分割します。出現頻度だけでなく色域の広がりもある程度拾うため、VNの絵では「全体の色味を保つ」方向に寄りやすいです。

PVNMではさらに、複数画像を1枚の縦長キャンバスにまとめてから代表色を取ります。これにより、背景と立ち絵が同じシーンで使う1つのパレットを共有できます。

## 固定パレット量子化

シーンパレットが決まったら、画像の各ピクセルをそのパレットのindexへ変換します。これは `engine.image_cache._quantize()` が担当します。

処理は次の形です。

```python
pal_image = Image.new("P", (1, 1))
pal_image.putpalette(flat_256_rgb)
quantized = img_rgb.quantize(palette=pal_image, dither=Image.Dither.NONE)
arr = np.array(quantized, dtype=np.uint8)
```

ここではPillowの固定パレット `quantize()` に処理を渡しています。Pillow側はC実装で高速化されており、固定パレットへの最近傍探索にK-D tree系の構造を使います。

PVNMの旧い純Python/NumPy方式では、概念的には全ピクセル `P` と全パレット色 `K` の距離を計算します。

```text
P個のピクセル × K個の色 × RGB 3成分
```

720x480画像で256色だと、単純計算では約8847万成分の差分を扱います。NumPyでまとめてもメモリ帯域と一時配列が重く、Python側の前後処理も効いてきます。

Pillow固定パレット方式が速い理由は、主に次の点です。

| 理由 | 内容 |
| --- | --- |
| C実装 | ピクセル走査と最近傍探索がPythonループではない |
| 探索構造 | 全色総当たりではなく、固定パレット用の探索構造を使える |
| 中間配列が少ない | `P x K x 3` の巨大な差分配列をPython側に作らない |
| キャッシュ可能 | 結果はパレットindex配列なので `.npy` に保存できる |
| Pyxelへ直送しやすい | `pyxel.Image.data_ptr()` にindex配列をコピーできる |

実装コメントでは、720x480の固定パレット量子化が純NumPy実装の秒単位からPillow経由のミリ秒級へ改善した、とされています。正確な値は環境依存ですが、設計上の本質は「重い最近傍探索をPythonからC実装へ逃がす」ことです。

## ディザリングをランタイムで使わない理由

ランタイム側の `engine.image_cache._quantize()` は `Image.Dither.NONE` を使います。これは意図的な選択です。

| 観点 | ディザなしの利点 |
| --- | --- |
| 速度 | 誤差拡散の追加計算がない |
| 再現性 | 同じ入力、同じパレットなら安定したindex配列になる |
| UIとの相性 | 文字、枠線、立ち絵の透明縁にノイズを増やしにくい |
| キャッシュ | `.npy`キャッシュが見た目どおりの最終indexになる |
| VN向き | 背景や立ち絵は静止画が多く、ディザの粒状感が目立つ場合がある |

一方で、滑らかなグラデーションではバンディングが出ることがあります。そのため素材作成段階では `VN Palette Tool` でFloyd-SteinbergやOrdered ditheringを選べるようにしています。ランタイムは安定性優先、素材変換ツールは画作り優先、という分担です。

## allowed_indicesと予約色保護

画像ピクセルに使わせたくないindexがある場合、`allowed_indices` を渡します。これは主にUI予約色を保護するための仕組みです。

Pillowの `quantize(palette=...)` は、固定パレット全体から最も近い色を選びます。すると、画像ピクセルがUI予約indexへ割り当たることがあります。PVNMでは必要に応じて `_remap_disallowed_indices()` が、禁止indexに落ちたピクセルを許可index内の最近傍色へ再マップします。

この再マップは全ピクセルで毎回総当たりしないよう、RGB値ごとの結果をキャッシュします。同じ色が多数出る画像では、同一RGBの最近傍計算は1回で済みます。

## 透明とcolkey

Pyxelの `blt` は、指定したcolkey indexを透明扱いにします。PNGのアルファをそのまま持つわけではないため、PVNMは透過PNGをindex画像へ変換するときに透明用indexを決めます。

`engine.image_cache._apply_alpha_colkey()` の設計は次の通りです。

1. アルファが128未満のピクセルを透明とみなす。
2. 不透明ピクセルが使っていないpalette indexを探す。
3. 空きindexがあれば、それを透明colkeyにする。
4. 全indexが不透明ピクセルで使われている場合は、選んだcolkeyと衝突する不透明ピクセルを別の近傍色へ逃がす。
5. 透明ピクセルをそのcolkey indexへ置き換える。

これにより、立ち絵ごとにユーザーが透明色indexを手で選ばなくても、PNG alphaをPyxelのcolkey描画へ落とし込めます。

エクスポート時は、この自動colkeyも `image_manifest.json` のcache recordへ保存されます。元PNGを同梱しない形式でも、ランタイムが同じcolkeyを取得できるためです。

## 画像キャッシュ

`ImageCache.get()` は、画像ファイルを表示サイズとパレットに合わせて `pyxel.Image` へ変換します。

キャッシュkeyは概念的に次の情報で決まります。

```text
正規化パス
表示幅
表示高さ
パレットhash
allowed_indices
alpha_colkey有無
```

ディスク上のキャッシュファイル名は `v2_<filehash>_<w>x<h>_<palettehash>.npy` のような形です。中身は `uint8` の2次元配列で、各値がPyxel palette indexです。

取得順は状況によって変わります。

| 状況 | 取得経路 |
| --- | --- |
| 編集中で元画像がある | 元画像mtimeより新しい `.npy` があれば読み、なければ生成 |
| エクスポート後で元画像がない | `image_manifest.json` が指す `.npy` を読む |
| Web/Androidでcacheが外部assets化されている | manifestの `external_cache.base_url` から同期取得またはprefetch済みbytesを読む |

`.npy` を使う理由は単純です。すでにPyxel indexへ変換済みなので、起動時やシーン遷移時にPillowでPNGを開き直し、リサイズし、量子化する必要がありません。配列を読み、`pyxel.Image` に直接コピーすれば表示できます。

## シーンパレットのキャッシュ

`engine.palette.build_scene_palette()` は、予約色と画像ファイルのmtimeからcache keyを作ります。

```text
cache_key = (sorted(reserved.items()), sorted((resolved_path, mtime)))
```

同じシーン状態で何度もパレットを作り直さないためです。VNでは、同じ背景と立ち絵の組み合わせが複数シーンにまたがることが多いため、このキャッシュは効きやすいです。

## 先読み

`engine/player.py` は、次に進む可能性があるシーンを解析し、背景/立ち絵の画像キャッシュを先読みします。

先読み対象は、次のシーン名、選択肢の遷移先、`goto` 先などから求めます。先読み時も実際のプレイヤーと同じ継承解決をシミュレートし、その状態の画像群からパレットを作ります。

先読みは、文字送り中や決定キーが押されている間は避けるようになっています。入力中に同期的な画像ロードを挟むと、テキスト表示の滑らかさが落ちるためです。

## エクスポート時の事前ビルド

エクスポートでは `engine.export._prebuild_image_manifest()` が、ランタイムで必要になる画像cacheを先に生成します。

通常プレイ時と同じルールでシーンを順に解決し、次を事前生成します。

| 対象 | 生成内容 |
| --- | --- |
| 背景 | 表示サイズに合わせたindex配列 |
| 背景flipbook | 背景と同じ表示サイズのindex配列 |
| 立ち絵 | 指定 `w/h` または画面内fitサイズのindex配列 |
| 立ち絵flipbook | メイン立ち絵と同じ表示サイズのindex配列 |
| エンディング | 画面内fitサイズのスライド画像 |
| タイトル背景 | タイトルボタン色も予約したパレットで生成 |
| ギャラリー詳細 | 画面内fitサイズ |
| ギャラリーサムネイル | セピアパレットの小画像 |

これにより、元画像を同梱しない軽量エクスポートでも、ランタイムはmanifestと `.npy` だけで画像を復元できます。

## VN Palette Toolの変換パイプライン

`vn_palette_tool.py` は、素材を事前にPVNM向けへ整えるツールです。ランタイムの自動減色とは別に、ユーザーが画作りを調整するための機能を持ちます。

`convert_image()` の大まかな順序は次の通りです。

```text
RGBA化
  ↓
透明maskを作成
  ↓
リサイズまたは倍率調整
  ↓
指定色透明化
  ↓
色補正プリセット
  ↓
ピクセル化、ノイズ低減、肌色補正、輪郭強調
  ↓
PVNM AUTO または CUSTOM .pyxpal のパレット決定
  ↓
色距離方式とディザリングを選んでパレット適用
  ↓
後ノイズ低減、孤立ピクセル除去
  ↓
透明トリム、キャンバス配置
```

### PVNM AUTO

PVNM AUTOは、現在の画像からパレットを作りつつ、UI予約色を保護する方式です。実装はランタイムのシーンパレットと似ており、透明部分を予約index 0の色で合成し、最大辺256pxに縮小してからAdaptive Paletteで候補色を抽出します。

`画像色` を `UI予約色を除外` にすると、画像ピクセルはUI予約indexを使わないように再マップされます。UI色と画像色の衝突を避けたいときに使います。

このとき、予約色と同じRGBそのものはfree slot側へ重複配置される場合があります。つまり「画像がその色に見える」ことは許しつつ、「画像ピクセルがUI予約indexを使う」ことは避けます。見た目の近さとindex保護を両立するための小さな工夫です。

### 色距離

VN Palette Toolでは、固定パレットへの最近傍判定に複数の空間を選べます。

| 色距離 | 内容 | 向いている用途 |
| --- | --- | --- |
| `Pillow標準` | Pillowの固定パレットquantize | 高速で安定。まず試す基準 |
| `RGB` | RGB空間のユークリッド距離 | 単純で予測しやすい |
| `Weighted RGB` | RGB各成分に重みを掛ける | 特定チャンネルを重視したい場合 |
| `YCbCr` | 輝度と色差へ変換 | 明るさを比較的保ちたい場合 |
| `Lab` | CIE Lab風の空間へ変換 | 人間の知覚に寄せた近さを使いたい場合 |

`Pillow標準` 以外は、`custom_palette_map_fast()` が処理します。ここでは全ピクセルをそのまま処理せず、まず不透明ピクセルのユニークRGBを取り、ユニーク色だけをパレットへ最近傍マップします。その後 `inverse` 配列で元のピクセルへ戻します。

```text
全ピクセル → ユニークRGB + inverse
  ↓
ユニークRGBだけ距離計算
  ↓
nearest色を決定
  ↓
inverseで全ピクセルへ展開
```

同じ色が大量に出るイラストでは、この方式で距離計算回数を大きく減らせます。

### ディザリング

VN Palette Toolでは次を選べます。

| ディザリング | 実装 |
| --- | --- |
| `なし` | そのまま最近傍変換 |
| `Floyd-Steinberg` | Pillowの `Image.Dither.FLOYDSTEINBERG` |
| `Ordered 2x2` | 2x2 Bayer風しきい値をRGBへ加算してから変換 |
| `Ordered 4x4` | 4x4 Bayer風しきい値をRGBへ加算してから変換 |

Ordered ditheringは、PVNM側で先に画像のRGBに規則的なオフセットを与え、その後はディザなしで量子化します。誤差拡散よりパターンが安定し、立ち絵やUI近くの素材で粒の制御がしやすいです。

## メリット

PVNMの現在の方式には次のメリットがあります。

| メリット | 内容 |
| --- | --- |
| 画面全体の整合 | Pyxelの1パレット制約下で、背景/立ち絵/UI/文字色を同居させられる |
| 速度 | 重い量子化をPillow C実装と `.npy` キャッシュへ寄せている |
| エクスポート互換 | 元画像がない成果物でもmanifestとcacheで再生できる |
| 予約色保護 | 話者色やUI色が画像に奪われにくい |
| 透明PNG対応 | 自動colkeyでユーザー作業を減らす |
| 調整余地 | VN Palette Toolで素材単位の画作りを追い込める |

## デメリットとトレードオフ

一方で、万能ではありません。

| デメリット | 理由 |
| --- | --- |
| シーンごとに色味が変わることがある | シーン画像群から毎回パレットを作るため |
| 画像ごとの完全最適よりは妥協する | 背景と複数立ち絵が1つのパレットを共有するため |
| 予約色が多いほど画像用の色数が減る | UI/話者色の保護と画像再現性はトレードオフ |
| ディザなしでは階調が段になる場合がある | ランタイムは安定性と速度を優先している |
| パレットhash違いでcacheが増える | 同じ画像でもシーンパレットが違えば別 `.npy` になる |
| Adaptive Paletteの結果はPillow実装に依存する | 完全な自前アルゴリズムではない |

## 改善するなら

将来改善する場合、候補は次のようになります。

| 改善案 | 期待効果 | 注意点 |
| --- | --- | --- |
| シーン間パレット共有の最適化 | 色味の揺れとcache数を減らす | 作品全体の解析が必要 |
| 重要領域の重み付け | 顔やキャラ色を優先できる | UIで指定する方法が必要 |
| 画像種別別の抽出比率 | 背景に立ち絵が負ける問題を調整 | 自動判定が難しい |
| Lab空間でのランタイム量子化 | 知覚に近い近傍色を選べる | Pillow固定パレットより遅くなりやすい |
| ディザ付きcacheの選択制 | グラデーションを改善 | 粒状感、cache増加、透明縁の品質確認が必要 |
| パレット生成結果の可視化 | デバッグしやすくなる | UIやログの追加が必要 |

現時点の設計は、VN制作ツールとして「画質」「速度」「実装の保守性」「エクスポート成果物の軽さ」のバランスを取ったものです。特に、PillowのC実装と事前生成cacheに寄せる判断が、PVNMの体感速度を支えています。
